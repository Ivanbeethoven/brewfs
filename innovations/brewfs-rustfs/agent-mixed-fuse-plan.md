# Agent-like mixed I/O through BrewFS FUSE

2026-10-20，测量前冻结的实验方案。36 次正式运行现已完成，结果见
[Agent mixed FUSE results](agent-mixed-fuse-results.md)。44/45 项性能门槛通过，
整套验收仍未通过。此状态更新不改变冻结的输入、配置或统计门槛。

目标：在大小不同的文件同时读写时，优化 agent 从挂载目录读取上下文、保存修改、
生成产物的完成时间，并与明确关闭动态联动的 `no-dynamic-block` 对照。
这里是可复现的合成 agent 文件访问轨迹，不冒充真实 agent 采样；不包含模型推理、
网络工具调用或编译时间。结果不外推到未测的 append、mmap、稀疏局部读取。

## 先明确两个被比较的方案

| 项目 | 无动态联动：no-dynamic-block | 动态联动：dynamic-auto |
|---|---|---|
| BrewFS 二进制 | 同一已验证二进制 | 同左 |
| BrewFS 运行时 hint | 不配置 | auto |
| RustFS 二进制 | 同一固定版本 cc4926f | 同左 |
| RustFS 接受 hint / fleet confirmation | false / false | true / true |
| BrewFS 完整对象读取/LRU策略 | 原有未启用 hint 的策略 | 当前 hint 模式的完整对象读取/LRU策略 |
| BrewFS 数据块 / chunk | 4 MiB / 64 MiB | 相同 |
| RustFS 新 q 布局写入 | 关闭 | 关闭 |
| 资源、缓存容量、预取、上传并发 | 完全相同 | 完全相同 |

主比较是**同一代码版本的运行时消融**。二进制均编译了可选 feature，基线在运行时
关闭；不能把基线描述成“历史 RustFS 官方版本”或“未编译 feature 的二进制”。
已接受的共同缺陷修复在两边都保留。当前 BrewFS 源码为 81db962，其运行代码与
7d3c366 相同；复用已验证 SHA256 为 dd5dc764…e7c7 的二进制，RustFS 为 dc5e70da…ffc9b。
完整哈希写入实验清单。每次运行使用新对象，禁止一边读取另一边的旧布局对象。

**重要边界：当前 auto 并没有改变 BrewFS 的 4 MiB 分块。** 它依据最终编码对象
长度选择 RustFS EC hint：不超过 1 MiB 时不发送，更大时请求 1 MiB。
这与本次服务器的默认 EC 大小相同。因此本比较检验的是已实现的整套读写联动，
不能单独证明“改变 EC 块大小带来提速”。每次记录实际对象大小、hint、EC 大小和
是否内联；若布局未变，报告明确写“布局相同，收益来自其他联动路径”。
以后若修改分级规则，应在相同混合轨迹上补充一次针对该规则的消融，不能偷偷
改变本轮对照含义。

## 主测试只有三个场景

| 场景 | 读 / 写操作比例 | 对应的 agent 行为 | 每个方案每轮操作数 |
|---|---:|---|---:|
| 浏览定位 | 90% / 10% | 读取源码、配置和索引，少量保存修改 | 8,000 |
| 编辑验证 | 70% / 30% | 多文件读取、保存修改、再次读取刚修改的文件 | 8,000 |
| 生成产物 | 30% / 70% | 创建输出、替换已有产物，同时读取上下文 | 8,000 |

比例按文件操作数计算，读字节和写字节也分别列出。三个场景始终四个并发 worker，
每个 worker 顺序执行 2,000 个操作，内部保留读写依赖；不再展开并发、块大小、
缓存容量、backend 和 direct-I/O 的主结果矩阵。

各场景都混合以下文件大小；**不是用同一个大文件替代所有大小，也不是分开跑
六个单一大小的吞吐测试**。每个 worker 的读集合和写集合都采用同一比例。

| 文件大小 | 操作占比 | 作用 |
|---|---:|---|
| 4 KiB | 40% | 小配置、小源码 |
| 64 KiB | 30% | 常见源码和文本 |
| 256 KiB | 15% | 较大源码、生成文本 |
| 1 MiB | 10% | 索引和中等文件 |
| 4 MiB + 64 KiB | 4% | 跨一个 BrewFS 数据块并带小尾块 |
| 16 MiB | 1% | 多块产物 |

每轮总逻辑 I/O 为 3,842.5 MiB；小文件占大多数操作，大文件承担较多字节。
按大小分别报告延迟和吞吐贡献，避免总体均值掩盖小文件退步。
这是预先选定的代表性合成分布，不声称来自真实用户追踪。

## 文件依赖、缓存和 FUSE 请求

- 预填充 1,000 个共享只读文件，另给每个 worker 500 个私有可写文件；同样采用上述
  大小分布，共 3,000 文件、1,440.9375 MiB。预填充全部走 FUSE，完成后严格排空，
  卸载再挂载，计时从客户端冷启动开始。RustFS/设备缓存不强行清空。
- worker 之间共享只读上下文；写入只作用于各自路径，避免不可控覆盖竞态。
  一半写操作原子替换已有文件，一半创建新产物。写操作为临时文件完整写入、
  fsync、close、rename；文件路径、内容版本和最终期望值提前生成。
- 读操作完整读取文件；优先安排约 20% 的读访问本 worker 最近写过的同大小文件，
  尚无对应写入时回退到普通读取。其余普通读取约 80% 访问各大小档的热集
  （该档 20% 文件），约 20% 访问其余文件。实际比例随冻结轨迹一起公布。
- 应用每次 read/write 的最大缓冲区固定 128 KiB，小文件使用实际长度。
  这是 syscall 上限，不假定内核实际 FUSE 请求也等于该值；记录 FUSE READ/WRITE
  次数、字节和实际可获得的请求大小分布。请求聚合/预取属于被测系统行为。
- 使用正常 buffered FUSE，direct_io=0、keep_cache=1、内核 writeback=false。
  一次场景内不反复卸载、不清缓存。保留真实的冷启动到热集演化，内核命中也计入
  用户任务收益；用 FUSE/S3 计数说明实际经过哪一层，不把纯内核命中称为 RustFS 收益。
- 固定伪随机内容、关闭压缩。读操作均检查完整长度和 SHA256；最后排空并重挂载，
  校验全部最终文件，核实已替换文件的最新版本和无残余临时文件。

## 单一部署与计时口径

原拟在杭州独占 ACS 环境使用 BrewFS 与 RustFS 各 performance 16 vCPU / 32 GiB。
测量前，两种 16 核客户端的 FUSE 设备预检失败，实际固定为 BrewFS 通用型 4 vCPU /
8 GiB、RustFS performance 16 vCPU / 32 GiB、Redis 1 vCPU / 2 GiB；RustFS 使用
四块 40 GiB ESSD PL1、EC 2+2。实际规格在正式采集前已写入 execution-bindings，
两组完全一致；结果文档保留预检失败、客户端网络上限和环境检查。
只做一次简短容量检查，作为环境记录，不加入产品主结果。旧环境结果不混入新统计。

固定 BrewFS 读内存 64 MiB、读 SSD 缓存 0、写内存 64 MiB、写暂存容量 1 GiB、
内存总预算 512 MiB；后台写回有效并发 3。暂存目录的实际设备及是否为临时盘需记录，
不能将 ACS emptyDir 未核实地称为本地 SSD。保留 stage-before-commit、持久化同步、
现行预取和已上传缓存设置；不以减弱持久化换取写入结果。

计时拆成三件用户能理解的事：

1. **任务完成时间**：四个 worker 同时开始到全部工作完成，包含轨迹执行、完整内容
   校验及正常间隙；没有人为 sleep。它衡量该合成文件任务，校验 CPU 时间另列。
2. **读/保存延迟**：每次 open 到 close，保存额外包含 fsync 和 rename；内容生成提前
   完成，读后 SHA256 不进入该文件 I/O 延迟。报告总体及每种文件大小的 p50/p95。
3. **含远端完成的总耗时**：任务结束继续等待既定四项写回债务连续三次为零，采样间隔
   20 ms；该完整等待计入结果。同时单列额外排空时间和债务曲线。fsync/close 延迟
   不冒充每个文件的远端持久化延迟。最多等 120 秒，超时按失败保留。

哈希采用有界缓冲并在每次读完成后立即处理，不保留整轮所有读取内容。它可能降低
极限带宽，因此另报 I/O 延迟和校验 CPU；两边执行同样的校验，所有时间和尾段保留。
不删除“网络重传多”“缓存未热”“结束阶段变慢”的样本。

## 配对与验收

一次正确性 smoke 后，主实验为 **2 个方案 × 3 个场景 × 6 个配对轮次 = 36 次运行**。
六轮顺序为 无/开、开/无、开/无、无/开、无/开、开/无；每对轨迹和内容完全相同。
场景顺序按轮循环，轮间更换预先固定的随机种子。每次重新初始化自己的数据集和
客户端缓存，保持相同服务端启动方式。所有正式 trace 和工具哈希在测量前冻结。
smoke 不计入性能统计，也不减少正式文件大小集合。

统计以轮次配对，不把 8,000 个文件操作当成 8,000 次独立实验；报告每轮值、
配对几何平均和按轮 bootstrap 的 95% 区间。保持既有门槛：

- 正确性、严格排空、重挂载和退出均通过。
- 相同工作量的含排空有效吞吐比（动态/关闭）区间下界至少 0.95；
  读与保存 p95 比区间上界最多 1.05。三场景及各大小档全部展示。
- 清晰收益要求吞吐点估计至少 +5%，且区间下界 >1；“编辑验证”作为预先指定的
  主要场景。三个场景和按大小的延迟守卫均无回退，才接受整套联动候选。
- 每档大文件样本少时区间会宽，记为证据不足，不合并独立轮次、不隐藏失败维度、
  不重复跑到通过。后续新候选使用新实验身份，原结果保留。

若涉及产品代码变更，先完成仓库规定的工作区正确性/编译检查，接受前再运行原样
compose 混合读写及 direct=0/1 守卫。它们单独放在回归附录，不扩成主比较表。
