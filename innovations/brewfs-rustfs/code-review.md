# Hint 协同代码 review 与恢复初始化修复

2026-10-20，基于上游 `947a349d387148f4520f22e64df5a8282329a9f5`。
本轮按用户要求收束性能采样，整理现有设计并修复已复现的问题。
既有性能结果继续有效于各自受测版本；下面的代码修复尚不代表新的性能收益。

## 已检查的协同边界

| 路径 | 结论 |
|---|---|
| `cadapter/s3.rs` 的 auto 与各上传入口 | 使用最终对象长度，PUT、分片上传创建和重试沿用同一策略函数。小对象不发送 hint；大于 1 MiB 的对象发送 1 MiB。保留简单策略函数，无需再引入策略工厂或通用 builder 抽象。 |
| `chunk/store.rs` 的完整对象读取和缓存准入 | auto 同时启用完整 GET 和相应缓存策略。共享下载包含缓存发布，避免晚到请求重复下载。flight 内再次查缓存用于处理并发竞态，并非可删除的重复检查。 |
| 后台预取和写后缓存 | 预取并发限制、短读检查与持久化缓存发布分别维护资源上限、内容完整性和排空语义。它们不是无作用的防御分支。 |
| `vfs/cache/write_back.rs` 的恢复状态 | 原实现将未完成初始扫描的空索引误认为“没有待恢复数据”。ACS 已用确定性回归用例复现，需要修复。 |

## 修复和精简

普通挂载构造启动后台恢复扫描后即可返回。新建 `FsWriteBackCache` 的内存索引为空，
但上次会话留在磁盘上的脏记录可能仍然存在。在扫描完成前，读取必须允许原有磁盘回退。

使用一个 `inventory_complete` 原子状态表达这个区别：初始为 false；成功扫描并插入所有
可恢复记录后，以 Release 发布完成，读取以 Acquire 检查。成功的空目录或不存在的脏目录
同样完成初始化；初始扫描错误或取消不会发布完成。普通恢复与 packed 恢复复用同一个完成函数。
索引清空后，仅当初始扫描已完成，才允许跳过磁盘回退。

两个构造入口共享基础初始化，避免为新状态维护两套字段赋值。普通恢复直接使用
`read_dir` 的结果，去掉先 `exists` 再 `read_dir` 的重复探测，并让非 NotFound 错误继续传播。
没有恢复已拒绝的按 inode/chunk 跳过扫描优化，也没有改变数据格式、fsync 要求或写入偏移。

顺带整理原有 overlay lint：合并相同条件的嵌套分支、将测试模块移到实现末尾；
外部来源的私有 spool 改为 Box，减少大枚举变体的内联体积，保持公开变体和所有权接口不变。
外部来源的构造增加一次堆分配；这项布局整理不宣称能提高端到端性能。

## 回归依据

原版与扫描候选都在 ACS 使用固定测试程序验证。原版通过“扫描前已有新封存记录”的读取用例，
被拒绝扫描候选返回 None；原版另在“扫描前没有任何新封存记录”的用例失败，证明初始空索引问题
是已有缺陷。新增测试覆盖有/无新记录、同步/非同步封存、完整覆盖读取、脏数据叠加、
空目录、扫描失败后重试，以及 packed 恢复完成后的清空行为。

测试在 ACS 16 CPU / 32 GiB 上串行运行，使用 Rust 1.99.0、单 Cargo job、单测试线程，
不等待 GitHub Actions。没有启动新的性能采样。编译完成不等于测试通过。

## 性能结论和简化后的主对照

主报告继续只有 no-dynamic-block 与 auto hint，真实 BrewFS FUSE 整文件混合读写。
三种比例为 90/10、70/30、30/70；六档文件同时混合为 4 KiB、64 KiB、256 KiB、1 MiB、
4 MiB + 64 KiB、16 MiB，操作占比 40/30/15/10/4/1%。保持固定资源、四并发、六配对轮次、
完整校验和后台上传排空。详细原协议见 [混合测试方案](agent-mixed-fuse-plan.md)。

no-dynamic-block 是同版本关闭自动协同的运行时消融；并非历史 RustFS 版本。
BrewFS 当前仍是 4 MiB 数据块，已测两组实际 EC 块都为 1 MiB；收益不能单独归因于动态块分级。
两档最大文件占 5% 操作但约 67.1% 字节，因此同时呈现各大小 p95，防止吞吐掩盖小文件保存回退。

恢复扫描候选的主对照吞吐提升为浏览 +12.61%、编辑 +9.47%、生成 +4.35%，但主门槛仅 44/45 通过；
相对旧 auto，浏览 256 KiB 保存 p95 变差 14.52%（95% 区间 +7.40%～+21.82%），修复自身收益不足。
该候选已拒绝并撤回，其 54 次记录和原门槛保留。这些数字不计为本次修复的性能证据。

未来写路径优化应从实际保存等待入手：生成场景关键工作者平均 21.21 秒，保存 18.32 秒，
其中 fsync 7.65 秒；读取只有 1.74 秒。stage 和 fsync 都含元数据及等待，不能当作纯磁盘时间。
调度合并仅是待验证假设，本 PR 不引入它。
