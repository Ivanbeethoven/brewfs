# BrewFS 根据已定型对象自动选择 RustFS hint

自动 hint 基于 `codex/rustfs-ec-block-size-hint` 的 `e779c079b4cdcf472645249ab79edd766efce58a`；整块读取联动基于后续 `de77445`。实现包含上传时按最终对象大小选择 hint，以及读取时的请求合并和缓存准入。下面分别保留实际完成的 ACS 对照与更广泛的实验设计。

## 从本地缓存获取可靠大小

写入链路为：文件写入 → 内存块及 SSD writeback 暂存 → 后台 uploader → `ObjectBlockStore::write_fresh_vectored_inner` 补零、压缩、加格式头 → S3 普通或 create-only 上传。恢复的暂存数据也通过块存储上传。

后台可能在文件仍被追加时上传已经定型的数据块。磁盘预分配量、文件当前长度、整个 slice 长度及缓存总占用都不等于最终 S3 对象长度。SSD 暂存是恢复源；选择 hint 时直接使用上传对象的准确字节数，避免扫描 SSD、增加 journal 字段或等待文件关闭。读取不需要重算 hint，RustFS 使用对象已持久化的 EC 布局。

当前写入器同时存在“先暂存再上传”和“暂存、上传并行”的路径，不能假设所有上传都发生在 SSD 写完之后。统一在 S3 入口决策可覆盖两者。一个暂存 slice 也可能拆成多个 S3 对象，hint 必须逐对象选择，不能只对整个暂存文件做一次判断。

## 精简策略

| 配置 | 上传行为 |
|---|---|
| 不配置 | 不发送 hint，保持服务端默认策略 |
| `auto`，最终对象 ≤ 1,048,576 bytes | 不发送 hint，保留小对象默认与内联策略 |
| `auto`，最终对象 > 1,048,576 bytes | 发送 4,194,304 bytes hint |
| 固定 65,536 / 262,144 / 1,048,576 / 4,194,304 | 每个新对象发送指定值，供明确覆盖和对照实验 |

此两档方案只提出减少大对象 EC 分段次数的假设。较大的 EC 块也可能增加工作内存；最终阈值必须由整对象读写结果判断。避免同时增加多个未经验证的小块档位、按缓存压力切换布局或修改 BrewFS 的块边界。

例如，不压缩的 4 MiB BrewFS 块实际为 4 MiB + 4 bytes：按 1 MiB EC 块需 5 段，按 4 MiB EC 块仍需 2 段。自动 hint 并没有消除格式头带来的短尾段，也不等于吞吐按 5/2 提升；这是需要实测 CPU、校验、磁盘和网络成本的机制假设。1 MiB 数据加格式头会从 2 段变成 1 段，高压缩率数据则可能两种策略都只有 1 段。

同一上传对象重试的选择稳定；小尾块独立决策；MPU 使用完整对象大小决定创建请求的 hint，而不是某个 part 的大小。普通、vectored、create-only、MPU、vectored MPU 五条路径共用一个选择函数。Cargo feature 默认关闭，未编译却配置 `auto` 或固定值时明确拒绝。

## 整块读取联动

配置 `auto` 或固定 hint 后，BrewFS 将同一冷块的 FUSE 片段读取汇入现有的完整 GET SingleFlight，并直接解析返回对象的帧头。这样一次下载可以覆盖后续片段，省去独立格式头探测和小 Range 与整块预取的重叠传输。完整响应沿用已有解码、长度与完整读取检查。

此模式下，现有 Moka 内存缓存采用 LRU，容量仍由原来的字节预算约束。文件系统会把完整文件读取拆成许多小 FUSE 请求；TinyLFU 中已经读完的旧块会积累访问频率，可能拒绝刚下载的新块，造成后续片段再次下载。LRU 让当前读取流的块进入缓存。未配置 hint 的挂载沿用原来的读取和缓存策略。

该组合面向整文件、整数据块工作负载。ACS 对照使用 4 MiB BrewFS 数据块和 64 MiB 读内存缓存。应用文件大小、实际上传对象大小和 RustFS EC 块大小分别记录；自动 hint 按编码后的对象大小选择，读取始终服从对象持久化的布局。

## 正确性标准

1. CLI 和 YAML 均接受 `auto`，CLI 优先；默认不发 hint；feature 关闭和非 S3 后端拒绝启用。
2. 0、64 KiB、256 KiB、1 MiB 前后 1 byte、4 MiB 前后 1 byte、MPU 和大对象之后的小尾块，实际 HTTP 请求元数据与规则一致。
3. 正常上传、重试、vectored 与 create-only 的请求字节完全一致；MPU 元数据只在创建时发送，重组所有 part 后字节一致。
4. 经真实 BrewFS 编码器的 LZ4、Zstd 及不压缩块，按编码后大小选择。包含 1 MiB 减 4 bytes 和减 3 bytes 的逻辑块，以检查 4-byte 格式头边界。
5. 在 ACS 的真实 RustFS 上检查 HEAD 返回的实际 EC 块大小，完整 GET 校验所有字节；再以 Redis + FUSE 验证后台上传、清债和重挂读取。服务端关闭 hint 时另测降级。
6. 默认和启用 feature 的工作区 lib/bin 测试、编译、clippy 和格式检查通过后，才接受实现。已知无关 all-features 基线失败单独保留，不宣称消除。

## 更广泛的性能实验设计

FUSE 文件尺寸至少包括 4 KiB、64 KiB、256 KiB、1 MiB、4 MiB、4 MiB + 64 KiB、16 MiB、64 MiB；另加格式边界正确性样本。每个文件尺寸都交叉无 hint、固定 1 MiB、固定 4 MiB、auto，保留固定 64/256 KiB 作为完整机制对照；不使用一个文件尺寸代表所有文件。

固定 BrewFS 4 MiB 数据块，分别测试不压缩的不可压缩数据和明确压缩率的 LZ4 数据。记录每个实际上传对象大小、EC 布局、PUT 数和完整 GET 覆盖范围。64 MiB 文件通常产生多个对象；按文件大小与实际对象分布分别展示，避免混为一谈。

主项目为完整文件写入及完整读取，包含冷 BrewFS 缓存和暖缓存、并发 1/4、后台上传模式及同步对照。写入同时报告应用阶段和上传全部完成的总耗时；必须确认 dirty/pending/inflight 清零，重新挂载后校验哈希。不得以 SSD 暂存速度替代远端持久化吞吐。

完整文件读取也要记录底层请求形态：FUSE/内核可能拆分读取，BrewFS 的缓存和预取设置又会影响最终 HTTP GET/Range。按实际覆盖的字节、请求数和下载放大报告。整块联动优化另保留固定 1 MiB EC 的对照，用来区分请求合并、缓存准入和较大 EC 块的贡献。

先做正确性和四轮机制筛选，再冻结九轮性能实验；相同主机、资源、数据、缓存设置和运行顺序。吞吐比的 95% 区间下界 ≥ 0.95，p95 延迟比区间上界 ≤ 1.05 为无明显回退门槛；明确收益要求吞吐几何均值 ≥ 1.05 且区间下界 > 1。保留失败、慢请求及不利结果，不拼接不同环境的历史样本。

报告必须列明文件大小、实际 S3 对象大小、测试标准、原方案与新方案的绝对吞吐/延迟、变化及区间，并画不同文件大小的整写/整读对比图。当前实现和正确性验证不等同于已完成性能验收。

## 2026-10-19 ACS 联动优化结果

本轮按整文件工作负载收敛范围：原 BrewFS `de77445` 不配置 hint，搭配原始上游 RustFS `7147063`；对照当前 BrewFS 联动实现与 RustFS `cc4926f`，配置 `auto`。RustFS 本轮没有新增源码修改。所有测试在 ACS 运行，WSL 仅编译。

两边资源相同：RustFS 8 CPU / 16 GiB，四块独立 40 GiB ESSD PL1，2+2 纠删码；BrewFS 4 CPU / 8 GiB，Redis 独立运行。BrewFS 块大小 4 MiB，读内存缓存 64 MiB、读 SSD 缓存关闭；写内存 64 MiB、SSD 暂存 1 GiB，不压缩。空客户端缓存指重挂并使用新缓存目录，服务器和云盘缓存保留。

主矩阵共 136 组：上述八种文件大小 × 并发 1/4，加 4 MiB 整文件混合读写；两个版本各四轮平衡顺序。每组完整写入、读取并校验 SHA-256，保留上传清债和完整缓存释放耗时。

| 指标 | 实际结果 | 限制 |
|---|---|---|
| 空客户端缓存整文件读取 | 16/16 场景明确提升并通过无回退门槛，配对吞吐为原版 1.393–3.417 倍 | 非冷服务器磁盘测试 |
| 整文件混合读写 | 吞吐提升 21.4%，通过无回退门槛 | 4 MiB 文件，4 并发，读写各半 |
| 整文件写入及上传完成 | 吞吐比 0.947–1.041，11/16 通过完整门槛 | 保留 5 个未通过场景，不宣称全面无回退 |
| 热缓存重复读取 | 吞吐比 0.936–1.040，9/16 通过完整门槛 | 内核缓存可直接服务，阶段较短 |

额外 16 组较长写入批次使用每组 2048 文件、4 并发、每版本四轮，未拼入主矩阵。4 KiB 写入吞吐比 0.990，95% 区间 [0.980, 1.000]；64 KiB 为 1.003，[0.992, 1.017]。两者均通过完整无回退门槛，但 4 KiB 的约 1% 下降仍保留。短批次约 100 ms 的指标更新粒度会影响上传完成耗时，不能将采样口径修正当成代码收益。

独立两轮消融中，保留整块合并和 LRU，只把自动 hint 换成固定 1 MiB EC 块：4/16 MiB 文件冷读中位数分别为 260.39/257.52 MiB/s，auto 为 271.85/270.60 MiB/s，下载放大均约 1 倍。主要收益来自减少重复读取及让新块进入缓存；自动 EC hint 在这些样本中进一步改善吞吐，不能把整体数倍提升全部归因于 EC 块变大。两轮消融只作为机制证据。

最终实现验证：hint 组合工作区 lib/bin 测试 1195 通过、227 跳过；feature 关闭时 1187 通过、225 跳过；格式、默认 check/build、两种组合 clippy 及 Tokio/io_uring 配置检查通过。两个新增测试分别验证并发片段共用完整 GET、流式压力下新块缓存准入，均完成先失败后通过。性能二进制 SHA-256：`70c6aca8f3c76c1836df0d2e6b6f367c8219cc51e4c50058ec6fafbb683006b1`。

中文图表及完整逐轮数据交付于本轮工作区 `outputs/brewfs-joint-optimization/`。以上四轮结果不等同于更广泛设计中的九轮、压缩和同步上传对照全部完成；MinIO 对照按用户要求后续补充。

### 环境边界和未完成项目

8 vCPU 构建 Pod 的设备白名单不允许打开 `/dev/fuse`；已成功的 1 vCPU Pod 允许打开，两者实际权限不同。其 5.10 内核又不支持默认 io_uring 运行时要求的同步取消，故实际挂载采用已有 Tokio 运行时。这些启动失败记录保留，不能解释为成功的性能样本。新部署必须在实际 Pod 上重新确认 FUSE 能力。

本次 RustFS 四个纠删码目录共用临时盘，并显式使用 `RUSTFS_UNSAFE_BYPASS_DISK_CHECK=true` 的测试开关，仅验证编码、上传与读取正确性。未验证独立磁盘的容错和存储性能。正式性能实验还需冻结合适的独立盘拓扑、资源规格、release 构建、运行顺序与缓存控制，然后执行上面的整文件/整对象对照；本表没有吞吐提升结论。
